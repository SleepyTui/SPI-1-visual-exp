# 设计同事工作流程

适用于本仓库所有 demo。设计同事只需要说项目名称、描述视觉修改、确认上传；终端与 Git 操作交给 Codex。

## 第一次使用：复制给本机 Codex

> 请帮我在这台电脑准备实验仓库 https://github.com/SleepyTui/SPI-1-visual-exp 。检查 Git、Node.js 22 或更新的 LTS、GitHub 访问权限；缺少工具时协助安装。先查找已有的这个仓库，有则复用，没有则克隆到当前可写的工作目录，不覆盖已有文件。需要我手动操作时只告诉我下一步点哪里，例如安装或浏览器登录，不要要求我输入终端命令。准备好后告诉我应在 Codex 打开的本地文件夹，确保后续任务在本机执行。读取 AGENTS.md、demos/README.md 和 docs/project-workflow.md，之后我会告诉你开始哪个项目。

首次准备需要操作者完成 Codex 登录、必要的安装确认，以及 GitHub 授权。Codex 无法替人完成登录。打开仓库根文件夹作为本地项目，之后不必每次克隆。新 demo 的额外依赖按其 README 安装。

## 日常只说两句话

开始工作（把项目名称换成想修改的项目）：

> 开始 MD 收藏家工作，并在电脑端打开视觉预览。

不用记完整名字或固定句式，说“打开 MD”“继续做收藏家”“打开那个封面编辑器”也可以。Codex 会结合仓库内容和对话定位。比如以后有一个 `fd-visual-demo`，且没有其他 FD 项目，“打开 FD 文件”就应定位到这个 demo 并打开视觉预览，不必要求用户补全目录名。这只是识别示例，不代表当前仓库已存在 FD 项目。

之后直接描述修改，例如“背景再暖一点，保持文字清晰”，查看页面并继续调整。每次修改先保存在当前电脑。Codex 在回复末尾提醒实际状态，例如：

> 这次修改已保存在本地，尚未同步云端。效果确认后，说“确认提交到云端”即可。

满意后说：

> 确认提交到云端。

“云端”在本流程中指 GitHub 源码仓库。这句话授权检查、提交并推送当前项目本次改动，创建或更新 PR；不包含合并到 main 或部署网站。如果还希望所有人从 main 取得这次修改，再说“确认把本次 PR 合并到 main”。

## 给 Codex 的执行步骤

### 识别项目并开始

1. 快速确认远端是 `SleepyTui/SPI-1-visual-exp`、当前分支和工作区；先读 `demos/README.md`，按下面的自然语言定位规则推断项目。索引不足时才查 demo 目录名、README 与入口标题；只有仍有实质歧义时才询问，不凭名称生成新项目。读取匹配目录的 README 与相关说明，后续搜索和修改以该目录为主。
2. 确认任务确实在用户电脑执行。云端任务无法直接打开用户电脑的 localhost，发现运行位置不符时明确说明，让用户切换本机任务，不返回假装可用的本机链接。
3. 拉取远端引用。工作区有改动时保留并继续当前工作，不切分支、不自动 stash、不覆盖或丢弃文件；不要因开工指令上传本地未确认的修改。有冲突或不确定的改动归属时保留状态，用简单语言说明。
4. 工作区干净且当前功能未完成时继续对应分支，安全同步远端；跨电脑接手未合并功能时先识别对应分支，不从 main 重新开始。多个可能分支或当前分支含其他项目未交接工作时，说明情况并确认要接手哪项；不得默默混合多个项目。
5. 开始新功能或当前分支已合并时，从最新 `origin/main` 创建唯一的 `design/<demo>-<主题或时间>` 分支。不要把旧测试分支文件带入设计分支；不得强制重置已有功能分支。
6. 按索引和该 demo 的 README 启动本机预览，使用对应 Action 或脚本。有桌面面板工具时打开到当前对话，否则打开本机默认浏览器。确认 HTML 和依赖资源可访问；无法确认浏览器实际画面时说明。若端口被其他目录服务占用，确认归属或换空闲端口，不结束其他项目。
7. 回复“可以开始修改〈项目名称〉了”和预览入口，避免输出整段 Git 日志。Actions 仅预览当前代码，不自动拉取、提交或推送；日常开工优先使用自然语言指令。

### 自然语言定位项目

- 不要求固定句式或完整路径。“开始……工作”“打开……文件”“继续做……”在设计工作上下文里都可以表达打开项目并预览；若用户明确要求查看源码文件，则按其明确要求处理。
- 优先考虑当前对话已经选中的项目和入口，再结合项目名称、常用简称、别名、目录前缀、README/HTML 标题及功能描述。忽略大小写、空格、连字符等格式差异。表内没登记的合理简称也可以识别；轻微错字或语音转写差异要结合其他证据判断。
- 若只有一个有充分依据的候选，直接打开，并顺带说“已按你说的 FD 打开〈实际项目名称〉”，无需再确认完整名称。不能只因仓库恰好有一个 demo，就把完全无关的名称硬匹配过去。
- 同一 demo 有多个入口时，优先选用户描述对应的入口或本对话上次使用的入口；无上下文时用索引默认入口，并给出另一入口。比如 MD 默认打开收藏家，“封面编辑器”打开工作台，不为同一项目的两个入口反复追问。
- 例如同时存在 `fd-poster` 和 `fd-gallery`，且上下文无法区分时，才问“你指的是 FD 海报还是 FD 图库？”不让用户提供技术路径。没有可信候选时简短说明未找到，并请用户描述项目用途；不擅自创建项目。

### 修改与提醒

1. 视觉调整先写入本机工作文件，保持原有交互与共享依赖。仅仅要求改视觉或打开预览，不授权提交、推送、合并或部署。
2. 每次完成一轮修改后，用一句话提醒真实状态。未 commit 时说“本地已保存，尚未同步云端”；已 commit 但未 push 时说“本地已提交，尚未同步云端”；已 push 时说“已同步到云端分支，尚未合并”；已合并则说“已合并到 main”。无改动时不用提醒上传，不能把文件保存说成 Git 提交。
3. 有未同步改动时，在本次回复中提示说“确认提交到云端”即可上传。不要为了提醒自行创建定时任务，也不要每轮都询问用户是否提交。

### 收到“确认提交到云端”

1. 根据当前对话确认正在编辑的项目；若没有上下文，按索引和实际改动定位，有歧义时只问项目名称。检查差异、分支和工作区，仅暂存本次项目相关文件及必要共享依赖，不混入其他 demo 的独立工作。若仍在 main 上，先创建功能分支；不得上传密钥、浏览器数据、缓存或无关文件。
2. 按改动范围执行最小验证，检查差异格式、修改脚本语法及入口和依赖。视觉或交互改动使用可用浏览器检查，不能用构建成功冒充视觉验收。MD 的原有 `verify.mjs` 和 `qa-collector.mjs` 含 Windows 绝对路径，先确认是否可运行；不能运行时报告限制，不伪称通过，不因此整体重配环境。
3. 提交、正常推送功能分支，创建或更新指向 main 的 PR，说明可见变化和验证。正常验证失败时先修复本任务内的问题；环境缺少工具时如实写入 PR。若推送被拒绝，检查远端新增提交，不强推。使用已有 GitHub 连接或凭据，没有权限时只说明需要哪一步授权，不要求粘贴令牌。
4. 拉取/查询远端确认推送成功，回复“已同步到云端分支，尚未合并”，附 PR。说明其他电脑继续这次未合并工作要接手该分支。用户未明确要求时，不合并 PR、不部署网站。
5. 如无待提交改动，检查是否存在未推送提交或未创建 PR；全部完成后直接报告当前同步状态，不创建空提交。

### 收到“确认把本次 PR 合并到 main”

1. 明确当前项目对应的本次 PR；多个候选时先确认。核对 diff、最新提交、验证结果与冲突，确认用户已认可视觉效果；有 CI 时等待必要检查通过。
2. 满足检查且权限允许时合并本次 PR，不绕过保护、不用管理员跳过检查、不合并其他 PR。阻塞时保留已推送分支、返回 PR 和一句原因。
3. fetch 并核实改动进入远端 main；干净的本地 main 只做快进更新，保留功能分支。回复“已合并到 main，其他电脑可更新”，附 PR 与提交。下一次开工再建新分支。不调用 Sites、不部署网站。

## Actions 与维护

- Actions 配置在 `.codex/environments/environment.toml`，跟随仓库同步。按钮取决于桌面版本；未出现时由 Codex 通过本地环境设置加载配置，仍不可用就执行对应脚本，不要求设计同事排查终端。
- 当前两个 MD Actions 使用 `scripts/preview.mjs`，仅依赖 Node.js 22+，没有 npm 安装步骤，支持 Windows、macOS、Linux。脚本复用同目录服务，默认端口 4199；并行检出可由 Codex 设置进程变量 `MD_ATELIER_PORT` 使用空闲端口。原收藏家 QA 仍默认使用 4199。
- 新增 demo 时更新 `demos/README.md` 的名称、别名、工作目录与预览方式，再按需添加 Action，通用口令保持不变。
- 收藏和星标等浏览器数据不会跟随 Git 同步；要带走可编辑的 MD 设计，先导出参数 JSON，在另一台电脑导入。
